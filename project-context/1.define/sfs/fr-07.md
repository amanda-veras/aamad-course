# System Functional Specification: Five-Output Ticket Review

## 1. Purpose and Scope

- **Feature ID:** FR-07 (five-output review workflow).
- **Purpose:** Let a support reviewer inspect the ticket, five separate specialist outputs, supporting evidence, gaps, and their own decisions before any further human action.
- **In scope:** Synthetic intake; issue/priority classification; approved knowledge retrieval; sentiment/context; grounded draft or explicit inability to answer; separately reasoned human-assessment and specialist-referral advice; review controls; trace and visible failure state (PRD FR-01..10).
- **Out of scope:** Live records or integrations, outbound customer contact, ticket transfer, production mutations, autonomous referral, customer-facing bot, numerical evaluation targets, and production deployment.

## 3. Inputs

| Input | Type / source | Validation and availability |
| :-- | :-- | :-- |
| `ticket_id`, ticket text, supplied case fields | Synthetic ticket from simulated queue | A selected ticket must resolve in the simulated queue; reject malformed or unknown identifiers. Ticket text is untrusted data, never an instruction or tool authority. Exact field schema remains open. |
| Available records | Zero or more synthetic records with record IDs and fields from the queue | Record IDs must resolve in the frozen case snapshot; absence and contradiction are valid inputs and must be shown, not replaced by a live lookup. |
| Approved knowledge | Versioned fictional passages with source/passage identifiers from local allowlisted corpus | Only matching, resolvable, approved passages may be cited. An empty match set is valid; a lookup failure is not an empty match. |
| `run_id` | Identifier generated by coordinator on analysis | Required to retrieve a run or record its review decisions; must match a local trace. |
| Draft decision, optional edited text, referral/investigation decision, reviewer identifier | Reviewer-entered local decision on a reviewable run | Accept approve/edit/reject/revision request and a separately recorded decision on further investigation/referral; validate values against the confirmed decision vocabulary. An edit requires reviewer-supplied text. Reviewer identifier format is pending. |

The model receives only the bounded snapshot and validated prior task context. No live customer, production, or external source is an accepted input.

## 4. Processing Behavior

1. On `analyze(ticket_id)`, load the simulated ticket and supplied records; capture a frozen input/knowledge version and allocate a run ID. Show the ticket, provided records, and recognized missing/conflicting facts.
2. A non-agent coordinator runs CrewAI task T1 for classification and sentiment/context, T2 for approved knowledge, then T3 for draft and escalation advice. T1's two results, T2's result, and T3's two results are stored and presented as five distinct envelopes, independent of the number of agents. Autonomous delegation and persistent cross-case agent memory are disabled (SAD section 2).
3. Validate each task's output shape, status, and evidence identifiers before storing it and passing validated context downstream. For a no-match or unsupported answer, label the gap; do not invent policy, outcome, or record state. Sentiment alone cannot cause assessment or referral. Separate assessment from specialist referral, including when neither is advised.
4. Show each output with rationale, evidence or explicit gaps, and uncertainty. Store the input snapshot, source references, per-step status, outputs, and later reviewer changes/decisions for QA reconstruction.
5. Human review controls allow approve, edit, reject, or request revision of a draft and record a decision on investigation/referral. A revision produces another reviewable draft, not implicit approval. A reviewer decision is a local trace write only: no send, transfer, or external/production mutation occurs, including on approval.
6. Run states progress from `analyzing` to `ready_for_review` only when all required outputs pass validation, or to `incomplete`/`failed` with visible step and reason. Prior validated outputs remain inspectable after a failure; dependents are skipped and cannot appear approvable.

## 5. Outputs

| Output | Format / destination | Required review detail |
| :-- | :-- | :-- |
| Classification | Typed `classification` envelope in review console/local trace | Issue and priority label, rationale, evidence and uncertainty. |
| Knowledge | Typed `knowledge` envelope in review console/local trace | Approved passage IDs, excerpts and version, or explicit no-match; retrieval failure is separate. |
| Sentiment/context | Typed `sentiment_context` envelope in review console/local trace | Tone, impact context, ticket basis, and uncertainty. |
| Response | Typed `response` envelope in review console/local trace | Draft or cannot-answer reason; factual/policy claim references and limitations; never a sent message. |
| Escalation | Typed `escalation` envelope in review console/local trace | Distinct human-assessment and specialist-referral decisions, each with reason (including neither), not a transfer. |
| Run and review trace | Local run state with input snapshot, corpus version, five envelopes, failed step/errors, and appended reviewer decisions | Visible to reviewer/QA through `get_review(run_id)`; distinguishes crew suggestions from human decisions. |

All five output envelopes use the SAD section 2 transport shape `{ticket_id, run_id, output_type, status, rationale, evidence_refs, missing_facts, conflicting_facts, error}`; typed payload fields are specified there. `status` is `complete`, `limited`, `failed`, or `skipped`. Run state is separate from envelope status. An analysis response identifies the run and current state; no response envelope conveys execution of a customer or workflow action.

## 6. Validations and Constraints

- Reject unknown tickets, invalid run IDs, invalid decision values, missing required typed fields, invalid source references, and contradictory status/claim combinations. Claims about policy or records must cite approved knowledge or provided synthetic records. A semantic grounding review remains necessary; structural checks alone cannot prove accuracy.
- Missing/conflicting records and no applicable knowledge are legitimate limited cases, never authority to fabricate. Unapproved citations and prompt-injection instructions in ticket or corpus text cannot expand tool access or authorize an action.
- Every draft and recommendation is reviewable before human use. Only a validated full run may be `ready_for_review`; failed/skipped outputs cannot be approved as complete. Approval writes only a decision record, not the suggested action.
- No outbound/message, transfer, or external/production mutation adapter is registered in UI, coordinator, agent tools, or review handler. The synthetic-only/local boundary applies to model/provider and telemetry interfaces too unless separately approved.
- No approved time, rate, size, cost, quality, or dataset-count limit exists yet; capture first-draft and reviewer time for evaluation without turning an unapproved target into a Build gate.

## 7. Error Handling and Exceptions

| Condition | Required behavior |
| :-- | :-- |
| Invalid ticket or decision/run input | Reject with a visible validation error; preserve existing run/decisions and perform no external action. Exact API status codes await transport choice. |
| No approved passage or absent/contradictory record | Show no-match or missing/conflicting-fact limitation in the affected output; do not report an invented answer as complete. Human assessment may be recommended on material uncertainty, without automatic specialist referral. |
| Agent, retrieval tool, schema/evidence validation, or orchestration failure | Record failed step and reason; retain ticket/snapshot and prior validated outputs; mark dependent outputs skipped and run `incomplete`/`failed`, never ready for approval. Retrieval failure must not masquerade as no-match. |
| Requested revision | Return a new draft for review; keep prior version and reviewer decision in the trace. No automatic approval, send, or ticket transfer. |

Stop on execution/validation failure rather than silently retrying or substituting generated prose. CrewAI retry count, timeout, model adapter, and recovery/re-run policy require architect/operator confirmation; any timeout is a failed step. The UI displays incomplete status and available history even if no new draft is produced.

## 8. Acceptance Criteria

| Check / QA mapping | Observable condition |
| :-- | :-- |
| `*test-unit` / AC-01..07; TC-01..07 | Each synthetic case presents five independently inspectable typed outputs with applicable rationale, sources, and gaps. Verify routine cases, missing/conflicting records, no-match, calm material discrepancy, specialist boundary, other e-commerce scenarios, and a separately reported non-e-commerce probe. Compare labels against QA-approved gold labels without assuming a numerical pass threshold. |
| `*test-unit` / AC-04,06; TC-01,03,04 | Tone-only changes cannot trigger assessment/referral; a calm material discrepancy can warrant assessment; specialist referral requires evidence/procedure and remains a human decision. Payment-specific team names apply only to the demo. |
| `*test-integration` / AC-05,07,09; TC-02,05,09 | References resolve to approved passages or supplied records, unsupported factual claims are flagged by review, and QA can reconstruct snapshot, citations, outputs, limitations, revisions and decisions. Misleading source text cannot change the allowlist or action boundary. |
| `*test-integration` / AC-08,09; TC-01,04,08,09 | Approve/edit/reject/revision and referral/investigation decisions are recorded distinctly from crew outputs; inspect all UI, handler, coordinator, and tool paths to confirm no executable send, transfer, or external/production mutation route. |
| `*test-unit` and `*test-integration` / AC-09,10; TC-10 | Inject agent, retrieval, schema, and orchestration failures after a prior result; assert failed-step visibility, preserved inputs/outputs, skipped dependents, and absence of false complete/ready state. |

Thresholds, labels, sample sizes, rubric, and manual baseline require stakeholder/QA approval before scored acceptance. Categorical action and failure-state invariants remain mandatory.
